# Agent notes

For a coding agent working in this repo. `README.md` and `CONTRIBUTING.md` are the human documents and are not duplicated here; read the non-negotiables in the README first.

Every task moves through four beats: isolate on a branch, build, prove with evidence, ship a PR carrying that evidence.

## State of the repo

The native shell is at M2 of `Mac_Shell_Plan` in the workspace: an AppKit app (`App/Sources/`) with one window holding a `WKWebView` on the bundled `ui/`, served through the `catchlight://app/` scheme (`UIResourceSchemeHandler`), never `file://`. The project is generated by XcodeGen from `project.yml`; the `.xcodeproj` is not checked in. `ui/` is copied into the bundle as a folder reference on every build, never by hand. Takes and Scripts live in an encrypted library on the Mac (M2, below); since M3b a Script is a Take of kind Script in the same store. CI is `.github/workflows/build.yml` (`macOS (Debug build)`): xcodegen, an unsigned Debug build, a universal-binary check and the unit tests, unsigned.

What M1 added, by file:

- `ShellBridge.swift`: the `catchlight` `WKScriptMessageHandlerWithReply` (page content world, main frame, `catchlight:` origin only) and the document-start script defining `window.catchlightShell` (OS version, `hw.model`). The page's half is `ui/bridge.js`; the message list is in `ui/README.md`, "The shell bridge".
- `NativeMenu.swift`, `Shortcut.swift`: the menu bar built from `catchlightMenu.model()`. The page pushes its model whenever it may have changed and `validateMenuItem` reads the latest push, because NSMenu validation is synchronous and `evaluateJavaScript` is not; `menuWillOpen` asks again and updates an open menu in place. A `role` maps to its AppKit selector with a nil target (`MenuRole`); every other item calls `catchlightMenu.run(id)`. A model whose structure changes (ids, roles, shortcuts) rebuilds the bar. Until the first push the bar is the app menu with Quit.
- `WebAddressBlock.swift`: the hard block on web addresses. A `WKContentRuleList` blocks every load that is not `catchlight:` (or the in-page `data:`, `blob:`, `about:`), and the page does not load until it has compiled. `NavigationRule` cancels every navigation off `catchlight://`; a link the user follows, `target=_blank` or `window.open` opens http(s) and mailto in the default app through `NSWorkspace`, never in the window. A content rule's `url-filter` has no `|`: a list using it fails to compile, and the window shows its error page instead of the app.
- `MainWindowController.swift`: transparent title bar over a full-size content view, so the page's toolbar is the title bar and the real traffic lights sit on it (`in-shell` on `<html>`, `full-screen` in full screen). Frame autosave as before; full screen is restored at launch. Safe Browsing lookups are off.
- `DebugLaunch.swift`: Debug-only launch arguments, compiled out of Release (Prove, below).

What M2 added, in `App/Sources/Vault/`:

- `Vault.swift`: the account. At launch `AppDelegate` opens it before the window loads (Touch ID or the login password; a cancelled unlock offers Try Again or Quit). First run stores the phrase, then the key (D-253, as the iPhone), then opens the library. A library stays only on a restore whose phrase opens it; otherwise it is moved aside (`Catchlight-before-<date>`), never deleted. Second device replaces the account the same way, without erasing anything first. The library folder is Application Support/Catchlight in the container, excluded from Time Machine (D-340).
- `Secrets.swift`: `KeychainSecrets` (the shared Keychain code) and `MemorySecrets` (tests, `-CLDebugAccount`).
- `Library.swift`: the page saves its whole Take list; the library diffs it against the SNAPSHOT the page's list came from (never against the store), upserts what the page changed and deletes what it dropped (leaving tombstones for sync). Sync writes the store while the page holds its list, so a diff against the store would delete every Take sync added and undo every Take it updated. Each snapshot has a generation (`Library.snapshot()`), sent with the library and back with every save; a save from an older snapshot is diffed against that one, and one too old to hold is refused. If the page and sync both changed a Take, the page's version is written and the pair goes to the conflict queue, as a conflict sync finds, and from then on the Take is held (M3, below); a Take the page deleted that sync changed since stays. `catchlightBridge.refresh()` hands the page the library as it is now, once no Take is held open (the editor, a Focus-ring or the reminder picker, `editingTake()` in `ui/takes.js`). A local edit to a Take sync deleted puts it back, as Core's own rule does (edit wins by timestamp, `SyncEngine.pullInbound`). If the library can't be read at launch, the bridge refuses every save and the page says so, so an empty page is never saved over a library it never saw.
- `TakeTranslation.swift`: the page's Take ⇄ Core's. The page's edit is laid over the stored Take through Core's own JSON coder, so fields the page doesn't model (block ids, delivery state, notification id, `anchorDay`, a place reminder's coordinates) survive. A content change the page didn't stamp gets a new `modifiedAt`, because sync settles conflicts by it. Ids are UUIDs (`newId()` in `ui/app.js`); anything else is refused.
- `ScriptTranslation.swift`: the page's Script ⇄ a Core Take of kind Script (M3b). One page block (a line, or a fenced code block or table kept whole) is one Core block; a `- [ ]` or `- [x]` line is a checklist item; the page mode is `pageMode` (continuous is none); `at` is the creation date (a date-only `at` from before M3b is that local day). The page doesn't stamp a Script's edits, so a content change gets a new `modifiedAt` here.
- `ScriptVault.swift`: Scripts as the Mac kept them before M3b, one AES-256-GCM sealed file each under Core's per-item key. At launch `Library.moveScriptsIn` moves each into the store with the same id, removing the file only once the Script reads back; a file that won't open, or whose id the store holds as a Take, stays.

What M3 adds so far: `App/Sources/Sync/SyncService.swift`, sync. It builds Core's `SyncEngine` exactly as the iPhone does (`Wiring.makeSyncEngine`: the open library's store, the account's keys, the folder, a per-install device id kept in `UserDefaults`) and runs one pass at a time off the main thread, opening the folder there too because a cloud provider can block; a request during a pass is answered as skipped. A page save, `reload`, the account commands and the flush's `ping` wait for a running pass (`whenIdle`): a save diffs against the store and then writes, and a pass writing in between would slip past the conflict check. Closing the window or quitting cancels a running pass so the last save isn't kept waiting. A pass asked for while one runs gets one more pass after it, so a save written at the end of a pass still reaches the cloud, and the request (Sync Now) resolves only when that pass has answered. It also makes the `Import` folder, as the iPhone does. Scripts (M3b) are in the same library and save through the same snapshot diff, each list touching only its own kind (`Library.PageList`); a save naming an id the store holds as the other kind is refused for that item. Take ⇄ Script is a change of kind on the same id (D-313, M3b step 2): the page asks the shell first (`changeKind {item, to}`, `Library.changeKind`), which lays the item in its new shape over the stored one, stamps it as an edit and puts the new version in every kept snapshot, and answers the item as stored so the page keeps what its own copy didn't carry (a Take from a Script carries only its text; its reminder, Important and order come from the stored item) (a sync change since the page's list goes to the conflict screen first, as a save's does), so the old list's save doesn't read it as deleted nor the new list's as new; then both lists move it. A Script is never the Obie. The conflict screen shows each side in its own kind and says Script when either side is one. They reach the folder only once `syncScripts` (UserDefaults, off) is on: the engine is built with `holdsScripts` from it, and with it off Core never uploads a Script, a Script's deletion stays on this Mac (its record is purged, since a record carries no kind), and a Take made a Script stays a Take in the folder (Catchlight-Core#22). Turn it on (`defaults write com.considus.catchlight.mac syncScripts -bool YES`) only once every phone reading the folder runs a build from 2026-10-01 or later (Script_Sync_Proposal, decision A). A refresh after a sync replaces the Scripts too (`replaceScripts` in `ui/app.js`), saving a Script edit still waiting for its debounced save first. When to sync is the page's (`ui/bridge.js`, where the sync setting lives), as on the iPhone: at launch, 5 s after a save, when the window comes forward (at most once a minute), every 15 minutes, and Sync Now (Settings and the File menu); Manual syncs only on Sync Now, Disabled never. After a pass that changed the library the page refreshes; failures and conflicts become Notice History entries in the iPhone's words. Conflicts (a Take changed on two devices, or a Mac edit landing while sync changed the same Take) wait in `ConflictQueue`, which, unlike the iPhone's, keeps each pair on disk, sealed under Core's per-item key in the library's `Conflicts` folder: a save that finds a conflict writes this Mac's edit over the version sync brought in, so the other device's version may exist only there until the user chooses (a conflict that doesn't open is kept, never deleted: a later write for the same Take first moves it aside to `<id>.<uuid>.unreadable`, which nothing reads or removes; as on the iPhone, either file still holds the Take named in it, which the page shows as read-only with no choice to make, and says so once a launch in Notice History). A save keeps its conflict on disk BEFORE writing this Mac's edit, and if that fails the save writes nothing and the page says so. A waiting Take is HELD until the user chooses, skipped or not and across relaunches (owner, 2026-10-07: "The file shouldn't update or edit until the conflict is resolved"): every pass gets `ConflictQueue.heldIDs` as `SyncEngine.sync(holding:)` (Catchlight-Core#27), so it neither uploads the Take nor writes the folder's version over it or deletes it, and a newer version from another device replaces only the pair's other side; `Library.save` refuses a change or deletion of it (answered in the save's `held`), but keeps a refused change that carries text as a NEW item beside it, with a new id and never the Obie (owner, 2026-10-08; answered in `forked`), and the page does the same for a draft open in the editor when the conflict arrives ("This Take changed on another device, so your edit was saved as a new Take."), while an unchanged or emptied draft writes nothing; a new Obie while the Obie is held, and `changeKind` of it; an imported Obie comes in as a standard Take while the Obie is held; and the page shows it read-only (`refuseHeld` and `keepHeld` in `ui/app.js`, the waiting ids injected as `catchlightLibrary.held`), putting back the STORED version (the `stored` side of each pair from `conflicts`, a refresh, or the launch library), never its own copy, which may hold an edit the shell refused. A held Take is never let go or forked when another device makes it a Script (Core 1.5.0, Catchlight-Core#29): with `syncScripts` on the Script arrives as the pair's other side; with it off Core leaves the Take as it is and names it in `SyncReport.heldConverted` on every pass, and `ConflictQueue.markConverted` marks the pair CONVERTED, in its sealed file, so the mark survives a relaunch and stays until the pair is resolved (it also changes the pair's `revision`). A converted pair is never resolved by re-stamping: that writes the Take's own id, and the next push sends the choice into the other device's Script (measured: the Script's file and entry are replaced, and the other Mac's Script turns back into a Take). Its only choices are `.asNew` ("Keep this version as a new Take": a new id and notification id, `createdAt` kept, stamped as a fresh edit, the Obie only if the original was, set after the original goes, as Core's private `fork`) and `.letGo`; both let the original go at once with `TakeStore.release` (no deletion record), so it can't be edited into the Script before the next pass, and `resolve` refuses a version pick for it (`choiceDoesNotFit`). The bridge sends a converted pair with no `remote`, and the sheet says "This Take was turned into a Script on another device." with only this Mac's version; after any choice the page drops its held copy before refreshing, so a save in between can't put the original back, and after a converted choice it drops the original from its list too. A let-go original is RETIRED for the launch (`ConflictQueue.retired`): saves and `changeKind` are given `saveRefusedIDs`, so an edit that still names it is kept as a new item and never written on its id, and a held id already gone from the store is skipped rather than refused. "Keep as new" records the copy's id in the pair's file before writing it, drops the pair once the original is released, and treats a failed Obie hand-over as costing only the marker, so a retry never makes a second copy. A pass reporting an ordinary pair for a converted id (the Script made a Take again) clears the mark and changes the revision. If a pass does let a waiting Take go (`deletedLocally`, `forkedFromScripts`), its pair and file go too (`ConflictQueue.release`; a damaged file is kept, renamed `.released`). Only `resolveConflict` writes it, and only for the pair the page read: each pair carries a `revision` that changes whenever a pass replaces it, and a choice sent with an older one (it waited behind a pass) is refused, the page says the versions changed and shows the new pair. The choice: the user keeps this Mac's version, the other device's, or both (owner, 2026-10-05), and the kept version is stamped as a fresh edit so the next push uploads it. A conflict file that doesn't open holds nothing, since it can't be shown or resolved. The choice screen is `ui/conflicts.js`: a banner in Dailies ("N Takes changed on another device." and Review) and a sheet with both versions, Local and Cloud, as the iPhone's `ConflictResolutionView`; Keep this version (once one is picked), Keep both, or Skip for now (hidden until the next launch or a sync finds it again, and still held). Until a choice, this Mac's version stands in the library, unchanged and not uploaded; its row says "Changed on another device. Choose a version to edit it.", and trying to change it asks "Resolve the conflict first" with Review. Unverified cloud copies are counted and noticed but have no choices on the Mac yet.

`App/Sources/Sync/NoteImport.swift`, Import notes, as the iPhone's `ImportCoordinator`: Markdown, plain text and RTF files from the `Import` folder inside the sync folder (Import Notes, File menu and Settings) or from files picked in an open panel (Import from a File, no sync folder needed), each through Core's `TakeImporter.parseDocument`, so a Catchlight export splits back into its Takes and a Script exported as one returns as a Script. Reading runs off the main thread; `Library.importItems` writes once any sync pass ends, adds the iPhone's summary Take, and the page refreshes and shows the iPhone's messages (`runImport` in `ui/settings.js`). Re-importing imports again, as on the iPhone. Nothing about the notes is logged.

`App/Sources/Sync/SyncFolder.swift`, the sync folder. The page's `shell.chooseFolder()` opens an `NSOpenPanel` sheet and gets back only the path to show; the security-scoped bookmark stays in `UserDefaults` (`syncFolderBookmark`) and opens as Catchlight-AppleStorage's `FileCloudFolder`, renewed when the system calls it stale. The shell is the authority on whether a folder is connected: `window.catchlightShell.folder` is the path it can actually open, and `ui/bridge.js` corrects the page's account record to match at load, so a deleted folder never looks connected. Erase everything, Second device, and first run choosing local storage (or finishing with no folder) forget the bookmark, as iOS lets the old account's folder go.

The page gets the library through `window.catchlightLibrary`, injected at document start (`ShellBridge.injectedLibrary`), and `ui/app.js`'s store reads Takes and Scripts from it in place of localStorage; saves and the account commands go through the bridge. `ui/bridge.js` loads first for that reason. The library script is a snapshot built when it is added, so `refreshUserScripts` rebuilds it before any reload (after a WebContent crash); a reload on the launch snapshot would save it back over everything written since. Before the app quits or the window closes, the shell calls `catchlightBridge.flush()`: a Take open in the editor is saved as a click outside it would save it, and the Script editor's debounced save goes at once (10 s timeout, so a page that never answers can't block quitting). The Mac picker offers time reminders only; a place reminder made on the iPhone opens and keeps its coordinates.

`ui/` holds the first-cut interface prototype (plain HTML/CSS/JS, placeholder data); read `ui/README.md` before touching it. The interface is shared with Windows, Linux and iPad (D-318), so keep it free of framework, build step and platform-only web features.

The macOS app follows the iOS app (`Considus/Catchlight-iOS`). It takes two packages, each pinned to an exact tag in `project.yml`: `CatchlightCore` from `Considus/Catchlight-Core` (data model, sync format, crypto; D-344) and `CatchlightAppleStorage` from `Considus/Catchlight-AppleStorage` (the encrypted SQLite store, the Keychain items and the BIP-39 wordlist, shared with the iPhone so the two can't drift; D-350). The tests also take `CatchlightCoreTestSupport`.

## Isolate

`Repos/` is one checkout shared by every concurrent session, so `HEAD` may be on another session's branch when you arrive. Check, then branch from the named ref:

```bash
git fetch origin
gh pr list -R Considus/Catchlight-MacOS
git checkout -b <type>/<short-name> origin/main
```

Stage by explicit path. Never `git add -A` or `git commit -a`. Read `git --no-optional-locks status --porcelain` before committing.

A fresh clone needs the committed hooks wired up once:

```bash
git config core.hooksPath hooks
```

`hooks/pre-commit` refuses commits on `main`; `hooks/commit-msg` refuses Claude attribution footers.

## Build

The non-negotiables in `README.md` are constraints, not house style: zero knowledge with nothing transmitted off the device, `kSecAttrSynchronizable: false` on every Keychain item, encryption always on, offline-first.

The crypto contract (domain-separation strings, derivation parameters, envelope format) is frozen and owned by `Catchlight-Core/Sources/CatchlightCore/Crypto/`. A Take written on the Mac must open on the iPhone. Never re-implement or alter those bytes here.

No third-party dependencies without agreeing it first.

The app is sandboxed (D-343) with the hardened runtime on. Its entitlements are `com.apple.security.app-sandbox`, `com.apple.security.network.client`, `keychain-access-groups`, and for the sync folder `com.apple.security.files.user-selected.read-write` and `com.apple.security.files.bookmarks.app-scope`, set in `project.yml` (XcodeGen rewrites `App/Resources/Catchlight.entitlements` and `Info.plist` from it, so edit `project.yml`, never those files). WebKit's helper processes crash under the sandbox without the network client entitlement, and the window stays blank; the page still loads nothing off the device: the content rule list and navigation policy (State of the repo, above) block every web address. Debug builds are universal (x86_64 and arm64) so they run on the Intel Mac; Release is arm64 only (D-317).

The app is signed for the team (YTPP9HU9F9, automatic signing) because `keychain-access-groups` is a restricted entitlement on macOS: only a provisioning profile grants it, and without it the data-protection keychain answers -34018. Xcode needs the Apple ID signed in (Settings ▸ Accounts) and this Mac registered; `-allowProvisioningUpdates` fetches the profile. CI builds with `CODE_SIGNING_ALLOWED=NO`, and its tests use `MemorySecrets`.

🚨 Pass `ONLY_ACTIVE_ARCH=NO` on the command line for a universal build. The project setting reaches the app target but not the package targets, which then build for one architecture and the app's other slice fails with "Unable to find module dependency: 'CatchlightCore'". For tests, `ONLY_ACTIVE_ARCH=YES` is faster.

```bash
brew install xcodegen            # once
xcodegen generate
BUILD_DIR="$HOME/CatchlightBuild"
xcodebuild -scheme Catchlight -configuration Debug -derivedDataPath "$BUILD_DIR/mac" -allowProvisioningUpdates ONLY_ACTIVE_ARCH=NO build
```

Keep derived data under `$HOME/CatchlightBuild`, outside the repo and the workspace.

Debug builds take launch arguments for proving the shell (`DebugLaunch.swift`; none exist in Release):

```bash
open "$APP" --args -CLDebugAccount YES -CLDebugNoExternalOpen YES -CLDebugEval 'return shell.systemInfo()'
/usr/bin/log show --last 2m --info --predicate 'subsystem == "com.considus.catchlight.mac"'
```

`-CLDebugAccount YES` opens with a throwaway account in memory and a library in a temporary folder, so the page opens on the main window and nothing touches the Keychain or the real library; `-CLDebugNoExternalOpen YES` logs the address a link would open instead of opening it; `-CLDebugEval` runs an async function body in the page once it has loaded and logs the result. In zsh, `log` is a builtin: use `/usr/bin/log`. Info lines need `--info`, and `log show` may not have kept them: `/usr/bin/log stream --info --predicate ...` running while the app does is reliable. Without `-CLDebugAccount`, the app uses the real Keychain and the real library, which on this Mac is the owner's.

The menu bar can be read and driven with System Events (needs Accessibility for the app running `osascript`):

```bash
osascript -e 'tell application "System Events" to tell process "Catchlight" to get name of every menu bar item of menu bar 1'
osascript -e 'tell application "System Events" to tell process "Catchlight" to click menu item "Storyboard" of menu 1 of menu bar item "View" of menu bar 1'
```

A menu item's tick is its `AXMenuItemMarkChar` attribute, which reflects the page's pushed model, so a click followed by reading the tick proves the round trip. Make the app frontmost (`set frontmost of process "Catchlight" to true`) before sending keystrokes.

Look for WebKit process crashes in the log if the window is blank: `log show --last 2m --predicate 'process == "Catchlight"' | grep processDidTerminate`. Debug builds set `isInspectable`, so Safari's Develop menu can inspect the page. If the window shows "could not start its web view safely", the content rule list did not compile; the log says why. The page's `localStorage` and the library live in the app's container (`~/Library/Containers/com.considus.catchlight.mac/`), separate from the browser's. localStorage holds only view settings; Takes, Scripts and the phrase never go there.

`ui/tlds.js` is generated, never edited by hand. After Core's TLD list is regenerated, run `python3 scripts/generate_tlds_js.py [path/to/Catchlight-Core]` (default `../Catchlight-Core`, the sibling checkout) and commit the result. It reads `Sources/CatchlightCore/Text/TLDList.swift` and never contacts IANA.

For `ui/`, serve it (`python3 -m http.server 8851 -d ui`, or the `catchlight-macos-ui` preview config) and prove changes in the browser with a screenshot in Night and Daylight. Clear `cl.*` keys from `localStorage` afterwards so the placeholder data is back to its defaults.

### The copy Mark runs

Mark runs `~/Applications/Catchlight.app`. Use `scripts/device/device.py`; never ask him which build he has or to export the log:

```bash
python3 scripts/device/device.py status                 # which build is installed, against origin/main
python3 scripts/device/device.py install --ref <ref>    # clean build of a ref, swapped into ~/Applications, stamp checked
python3 scripts/device/device.py logs --crashes         # diagnostics log and crash reports, as text
```

- **`install` after an app change merges**, with `--ref origin/main`, so Mark runs what was merged. Run it in the background (`run_in_background`): a clean universal build takes several minutes. It builds in a throwaway worktree, never the shared checkout; quits the app if it is open; keeps the previous copy until the new one reports the commit that was built, and puts it back if not. Only one install runs at a time. Ask Mark first when the build crosses a data-affecting change (a Core bump, the store, the Keychain, sync), because his real library is in this Mac's container.
- **The build stamp:** `project.yml` stamps `CFBundleVersion` with the git short SHA, as the iPhone app does, on a clean build only: an incremental build into existing derived data reads "1", and so does a copy built before the stamp existed. `install` always builds clean. A local build with uncommitted changes is stamped `<sha>+dirty`, which `status` reports as not a commit it knows; `install` refuses to build one. When `status` reads "1" or a `+dirty` stamp, install a fresh build rather than guessing which one it is.
- **`logs` when Mark reports a problem**, before asking him anything. It reads `catchlight-diagnostics.json` from the app's container (no Take content, by design), writes it as text, and with `--crashes` adds Catchlight's reports from `~/Library/Logs/DiagnosticReports`.

## Localisation

The app reads in English or one of the iPhone's 18 languages (es, fr, de, zh-Hans, zh-Hant, da, nl, fi, it, ja, nb, pl, pt-BR, pt-PT, sv, th, tr, ko), in two String Catalogs:

- `ui/l10n/Localizable.xcstrings`: the page, through `t()` in `ui/i18n.js`. How it works and how to add a string: `ui/README.md`, "Localisation". The menu bar's labels come from the page's model, so they are translated there.
- `App/Resources/Localizable.xcstrings`: what Swift shows itself (the unlock alert, the open panels, the sync notices, the Keychain prompt's reason, the bar before the page's first push, the web view error page). Text built in Swift is `String(localized: "…")` with the literal inside the call. The import summary Take stays English, as the iPhone writes it, because it is stored and syncs. Diagnostics stay English too: a bridge reply such as "save needs a list", `Library`'s error details, and `ConflictQueue`'s "changed while you were choosing", which `ui/conflicts.js` matches.

`ShellBridge.preferredLanguage` is `Bundle.main.preferredLocalizations.first`, the bundle's own choice for `String(localized:)` among the `.lproj` folders the catalogs build, and the page gets it as `catchlightShell.language`, so the page and the native text always agree. Window and Help are found by an item they hold, never by title. The test scheme runs in English (`language: en`); a test that wants another language sets `ShellBridge.language` (`LocalisationTests`).

After touching a string, run `python3 scripts/l10n/check_catalogs.py` (a unit test runs it too): it fails on a key the code uses that a catalog lacks, a key nothing uses, a missing language or plural form, and a translation whose placeholders differ from the English. A translation copied from the iPhone is `translated`; one written here is `needs_review` until a speaker has read it. To see a language: `open "$APP" --args -CLDebugAccount YES -AppleLanguages '(de)'`.
